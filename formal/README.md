# Formal models

TLA+ is used for bounded state and transition properties, not to claim a proof
of the entire RaptorQ codec.

Good model-checking targets are:

- partition and parameter-bound invariants;
- least-eligible K' selection and source/padding/repair ID translation;
- incremental decoder lifecycle, duplicate handling, and completion safety;
- source-block bookkeeping under reordered arrivals;
- cache/concurrency behavior if encoding plans are shared later.

GF(256) arithmetic, table transcription, tuple outputs, and matrix elimination
are better checked with exhaustive Go tests, algebraic properties, and
differential vectors. TLC cannot establish byte-level RFC interoperability.

`Partition.tla` checks every pair within configured bounds in one model. Run:

```sh
task verify:tla
```

`SystematicMapping.tla` explores a bounded table with gaps and proves least-row
selection, source-ID identity, repair-ID padding skips, and absence of an ESI
for an implicit padding ISI. `MappingTrace.tla` replays Go-generated boundary
records for every real Table 2 range. A forged final mapping is required to
fail `TraceComplete`; deleting the final boundary record must independently
fail `TraceCoverage`.

`PlannerProgress.tla` exhaustively ranges over every covered incidence relation
on a bounded row/column universe. It proves the structural phase-one argument:
when selecting a row removes every still-active column incident on that row,
each remaining column retains an active incident witness row, so a nonempty
active-column set cannot stall. A mutation that deactivates a selected row
without removing its incident columns must violate `NoPlannerStall`. Go tests
separately establish the required initial V-column coverage from `G_LDPC,1`
and `I_S` for all 477 real Table 2 rows.

`DecoderLifecycle.tla` exhaustively checks a bounded abstract incremental
decoder, including the authenticated `decoded -> verified -> delivered`
boundary. Generated traces cover delivery, abort, verification failure, and
state-preserving rejection of failed calls in pre-ready and terminal states.
Negative controls contain an illegal premature decode, an early delivery, and
the previously accepted post-terminal reject; the verification task requires
TLC to reject all three for `TraceComplete`.

`DecoderLifecycleMutation.cfg` enables a deliberate transition that forges
verification and delivers directly from `decoded`. The negative verification
gate requires this mutation to fail exactly `EveryNextTransitionAllowed`,
preventing the allowed-action checks from becoming one-sided or vacuous.

`ObjectDecoderTrace.tla` complements that abstract exploration with traces
generated by the public Go object decoder itself. Shortened source symbols for
a two-source-block, two-sub-block object drive the production decoder through
completed-block counts `0 -> 1 -> 2` and `receiving -> decoded -> verified ->
delivered`. The verifier observes the exact OTI, object length, context, and
candidate bytes; delivery separately observes the public `verified` state
before the delivery counter advances. A post-terminal packet is rejected
without changing state. Separate implementation traces cover verification and
delivery failure. A deterministic one-block trace feeds the fixed
rank-deficient repair ESI set 319 through 328 under a one-attempt cap, observes
ESI 329 produce `decode-failed`, and proves a subsequent add is rejected while
preserving that state. Negative controls verify too early, remove the verifier
observation, expose delivery in the decoded state, corrupt the authenticated
binding, and forge recovery from `decode-failed`; each must fail the exact
`TraceComplete` property. Because callbacks inspect `State` while they run,
this also proves those observations are made without holding the decoder mutex
for the recorded execution.

`SparseScheduleTrace.tla` replays observations from the production sparse
schedule owner. It checks aggregate logical backing reservation, row/column
mapping bijections and inverses, coupled swaps, mapping-neutral row addition,
operation cursor order, and state preservation after capacity/index rejection.
Its negative controls delete a required operation, forge a row swap without
the mapping update, and accept an allocation at one byte below the calculated
backing requirement. Sparse coefficient algebra is intentionally checked by
the dense Go oracle rather than duplicated in TLA+.

`InactivationTrace.tla` replays phase snapshots emitted by the bounded eager
five-phase solver for an overdetermined RFC source system. It independently
recalculates the declared logical-backing estimator, checks one-byte-short
preflight rejection, binds the initial `u` to the RFC `P` parameter, checks
the exact phase-one `i'=i+1, u'=u+r-1` update, `i+u <= L`, and the exact
`M-L` discard count, ordered phase boundaries, and terminal completion only
after phase five. Negative controls delete phase three, forge the discard
count, accept the under-budget solve, forge the initial budget, forge the RFC
initial `u`, and forge a later phase-one `u` update. Dense
tests independently check final
solver results, while matrix-container tests compare individual sparse
mutations. The production hybrid residual and substitution path is bound by
the `HybridTrace.tla` trace described below; the eager trace remains focused on
its phase and resource-accounting contract. Another
negative permutes phase labels while retaining numeric snapshots, proving the
record labels themselves are bound to the ordered phase transitions. The trace
does not duplicate GF(256) algebra in TLA+ and does not measure allocator or
runtime heap peaks beyond the implementation's declared logical-backing model.

`HybridTrace.tla` is the implementation-bound bridge from the immutable
phase-one plan to hybrid execution. Its generated K'=10 corpus uses received
ISIs 0 through 11 and records the production planner and executor at their
exact independent workspace limits. The model reconstructs pivot selection,
frozen and elimination incidence sets, consumed sparse incidences, coupled row
and column permutations, the replay cursor, the binary dense suffix, the
13-by-11 dense residual transition, ordered substitution dependencies, and the
canonical Figure-5 right-hand-side row map. It independently recalculates both
logical-backing formulas and requires a one-byte-short rejection for each
phase. Negative controls delete a replay event, forge frozen and elimination
events, forge an observed permutation or binary snapshot, enter dense
completion early, corrupt a substitution row or dependency, accept each
one-byte-short budget, forge the RHS map, and alter an observed residual
coefficient, dense solution, or final result. Replay maps, binary/HDPC rows, working
right-hand sides, the materialized residual system, dense solution,
substitution operands/results, immutable input, and final result are emitted as
deep-copied values at production executor mutation points; normal execution
passes a nil observer and an allocation regression requires the substitution
trace hook to remain zero-cost. The generator byte-compares every production
binary snapshot with an independent replay, checks every coupled non-HDPC and
HDPC equation plus every residual equation against a known solution, checks the
dense solution byte-for-byte, and verifies each substitution XOR.
TLC binds the small residual/RHS/solution/input/result byte corpus to the exact
stage sequence and shape. The task gate pins each control to its exact TLC
invariant or temporal-property failure; GF(256) multiplication itself remains
covered by exhaustive Go algebra and external oracle tests rather than being
reimplemented in TLA+.

For a focused model run, use the checked launcher from the repository root:

```sh
scripts/tlc.sh -noGenerateSpecTE formal/DecoderLifecycle.tla \
  -config formal/DecoderLifecycle.cfg
```

`task verify:tla` first checks the pinned jar hash. The focused launcher always
selects that project jar and a Java 17+ runtime but does not independently
recheck its hash.

The trace technique checks finite safety behavior. It is not end-to-end code
verification and does not establish liveness of the real implementation.

The launcher places TLC metadata in a temporary directory outside the module
tree and removes it on every exit, including expected negative-control exits.
